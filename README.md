DSH 桌面版（Windows 优先）的长期记忆插件 —— **纯本地、零依赖、零 shell、零外部服务**。

## 1. 为什么写它

现有四个记忆插件（`dsh-memory`、`dsh-auto-memory`、`dsh-memory-evolve`、`hindsight`）默认面向 Linux/macOS，在 Windows 上表现不好。把四份审查报告交叉后，问题归为**三类**（并非都是"硬编码 shell"）：

| 类别 | 具体形态 | 出处 |
|---|---|---|
| **路径 / 环境** | 根目录在**模块加载期**求值：`const HOME = process.env.HOME ?? ""`。Windows 上 `HOME` 通常未设（用 `USERPROFILE`）⇒ 空串 ⇒ 全局层路径变成 `/.dsh/memory/topics`，**整体静默失效** | dsh-memory A3 |
| | `update.js` 用 `process.env.HOME ?? ''`，退化成**相对路径** `.dsh`，随 CWD 漂移 | dsh-memory-evolve B8 |
| **shell 依赖** | 硬编码 `/bin/zsh`，且 `execFile` 的同步抛出**未被捕获** ⇒ 钩子抛穿、进程崩溃（实测 `spawn EPERM` 起） | dsh-memory A1 |
| | `sh -c` + `child.on('error')` 静默吞错 ⇒ 通知**永远不触发** | dsh-memory-evolve C10 |
| | `process.kill(-pid)` 依赖 POSIX 进程组 ⇒ Windows 上承诺的"进程树终止"不成立 | dsh-memory-evolve B7 |
| **外部进程语义** | 注入回调里每步 `spawnSync('git', ...)`，失败**静默** catch ⇒ 分支隔离静默失效 | dsh-memory-evolve B2/B3 |

**关键推论**：只要做到「零 shell、零外部进程、路径全走 `node:path` + `homedir()`/`DSH_HOME` 且**调用时求值**」，就已经绕开上述全部三类失效 —— 因此本插件**不需要为 Windows 写任何 `if (platform)` 分支**。

注：`dsh-memory-evolve` 是四个里唯一真做了跨平台处理的（`process.platform` 分支），所以问题不能一概而论；它的 `memoryDir` 解析（`DSH_HOME || homedir()`）是四个里唯一写对的。

## 2. 采用的机制（以及来自谁）

核心取舍来自 `dsh-memory`：**注入的只有地图，正文永远按需检索。**

```
~/.dsh/memory-win/global/*.md           ← 全局层（跨项目通用）
<repo>/.agent-memory/*.md                ← 项目层（随仓库走，默认被 .gitignore 忽略）
```

每个 `*.md` 是一个**主题分片**，首行可选关键词头，正文是条目：

```markdown
<!-- windows-paths · pwsh git-bash 路径 引号 -->

## 坑

- [2026-09-28] pwsh 里读文件用 Get-Content -Raw；不要用 cat
- [2026-10-01] git bash 下路径要写成 /c/项目 而不是 C:/项目
```

条目格式是唯一硬约定：`- [YYYY-MM-DD] 事实`。日期经 **UTC 回读校验**（`new Date("2026-13-45")` 会进位到 2027-02-14 而不是 Invalid Date，只判 `NaN` 会把这类错误放行）。

> **项目层目录名是 `.agent-memory`。** 去掉产品前缀是因为目录里放的只是明文 markdown，任何 agent（Claude Code、Codex、Cursor 等）都能直接读，不需要认识 DSH。保留前导点、作为隐藏目录，是仓库里"工具产生的数据目录"的通行惯例（`.git` / `.vscode` / `.claude`）—— **隐藏不等于不可读**，别的 agent 用绝对路径或 `ls -a` 一样能读。

### 记忆可以被**修正**（不只是追加）

每条存活条目都有一个由「日期 + 正文」派生的 **4 位 id**（例 `a3f1`）。`memory_correct` 用它取代一条已经错了的记忆：

| `reason` | 用在哪 |
|---|---|
| `defect` | **发现缺陷** —— 你之前记的结论/实现本身是坏的 |
| `overturned` | **之前结论被推翻** —— 当时对，现在证明不成立 |
| `correction` | **用户纠正**了你 |
| `retract` | 结论不再成立，且**没有**新结论（纯撤回） |

取代的语义是**保留历史 + 让旧结论失效**：

```markdown
<!-- - [2026-09-30] 项目层守卫不用单独覆盖，tools.guard 就够了 -->   ← 就地注释：保留历史，行号不变
- [2026-10-02] 项目层必须单独覆盖：tools.guard 回调原来只查了全局层 [fix:overturned of #bc32]
```

被注释的旧条目**不再进地图、也不再被 `memory_search` 命中** —— 这一点是"结论被推翻"能真正生效的关键。只追加新条目是不行的：旧结论会继续留在上下文里误导后续判断。

**拿 id 的两条路**：`memory_search` 命中即给 id；若关键词搜不到（比如它就是不含你关键词），用 `memory_list { entries: true }` 列出全部条目及 id。这条兜底路径是必需的 —— 否则"检索不到的记忆永远无法被修正"。

修订既有条目只能走 `memory_correct`，`write`/`edit` 直改记忆文件会被守卫拒绝。

### 注入档位：地图档

| 状态 | 注入内容 |
|---|---|
| 某层条目 ≤ 8 | 逐条**内联**（含 `#id`，便于直接修正），并标注档位；**每条正文截断到 160 字符** |
| 某层条目 > 8 | 每片一行：`片名：N 条 ｜ 最新日期 ｜ 片路径 ｜ 关键词`（此时取 id 需 `memory_search` 或 `memory_list entries=true`） |
| 完全为空 | 仍注入**纪律块**：否则模型不知道记忆功能存在，就永远不会有第一条 |

### 片路径是**层内相对**（P2a）

地图里的片路径是**相对该层目录**的短路径（就是 `片名.md`），不是绝对路径。

原因：原先每片都写整条绝对路径。实测数据（12 片 / 60 条，走地图档）：**整段地图 2,392 字符，
其中分片行占 1,602 字符（67%），而分片行里有 63% 是路径** —— 全是每片重复的同一段层目录前缀。
改成层内相对后，**片行平均从 134 字符降到 68 字符（−49%）**。

**层目录在哪**（按注入实际渲染，别照直觉猜）：

| 层目录 | 在注入里的位置 |
|---|---|
| 全局层 | **段尾统计注释**：`<!-- 记忆合计 N 片 / M 条 · 全局层 <绝对路径> -->`（两种档位都有） |
| 项目层 | **只有小层内联档**才有：`### 项目记忆` **下一行**的 `<!-- 本层条目少（N 条），已逐条内联；细分片路径 .agent-memory -->` |

⇒ **地图档（某层 > 8 条）下，项目层的层目录不在注入里** —— 片路径此时是层内相对，
拼不出绝对路径。需要绝对路径时用 `memory_list`（片路径仍是相对）或直接
`memory_search`（命中项本来就给绝对路径），照常能取到文件。

> ⚠️ **一处形态差异，别混**：`path=` 在不同工具里含义不同 ——
> - **地图 / `memory_list`**：片路径 = 层内相对（省字符）
> - **`memory_search` / `memory_list entries=true`**：`path=` = **绝对路径**
>
> 因为后两者的路径是直接喂给 `read` 的，相对路径会被解析到会话 cwd 下、读不到文件。
> 这是刻意的分工：**展示用相对、取文件用绝对**。

### 片级关键词：只在**新建分片**时可设（P2b）

`memory_add` 接受一个可选 `keywords`，写入新建分片的**首行**：

```markdown
<!-- windows-paths ·  pwsh git-bash 路径 保留字符 -->

- [2026-09-01] pwsh 里读文件用 Get-Content -Raw
```

它进地图的 `关键词：…` 段，是模型**不打开分片就能路由**的唯一线索。

**为什么不做自动提取**：实测朴素 n-gram + TF-IDF 在低条目量语料上只会产出
`不再`/`要用`/`就绪` 这类实词碎片，而把真正有路由价值的标识符
（`mkdtempSync`、`spawn EPERM`、`setBundleEnabled`）压掉。**噪声比"（未设置）"更糟** ——
后者至少诚实。所以关键词由调用方在**最清楚这片要装什么**的那一刻给出。

| 行为 | 结果 |
|---|---|
| 新建分片 + `keywords` | 写入首行；地图立即可见 |
| 新建分片**不带** `keywords` | 照常写入，但结果带 `warning`（不阻断） |
| **已存在**的分片传 `keywords` | **拒绝** —— 关键词头是首行，而 `memory_add` 只追加不重写首行 |
| 只有头行、0 条目的文件 | 仍算"新建"，允许补 `keywords`（不会写出第二个头） |

**头行只有档位、没有统计数字。** 统计（`记忆合计 N 片 / M 条`）刻意放在**段尾**：头行在系统提示词最前面，一放"N 片 / M 条"这种每写一条就变的数字，整个前缀就失去缓存。这条纪律来自 `dsh-memory` 的实测（写一条记忆后子代理首轮 `cacheRead` 从 85% 掉回 0%）。

### 五个工具

| 工具 | 作用 |
|---|---|
| `memory_list` | 列出两层地图（片名 / 条数 / 最新日期 / 关键词 / 路径 + 归档件数）；`entries: true` 时列出**全部条目及 id** |
| `memory_search` | 按关键词跨层检索，**命中带 `id` / 文件 / 行号** → 直接用 `read offset=` 取原文 |
| `memory_add` | 追加一条，经格式 / 日期 / 凭据三项校验 + 原子写；新建分片可带 `keywords` |
| `memory_correct` | **取代**一条已错的记忆（`defect` / `overturned` / `correction` / `retract`），旧条目就地失效 |
| `memory_cleanup` | **容量策略**：把已失效条目与空分片搬进归档目录，并报出搬了什么、去了哪（0.2.4） |

`memory_search` 是**纯 JavaScript 子串匹配**（空格分词为 AND 语义，中文无需分词），不调用任何模型、不做向量检索 —— 因此**零额外 LLM 成本**。

### 容量策略：归档（0.2.4）

这是 0.1.x 唯一**会随时间单调恶化**的缺口：地图随分片数线性增长，而被取代的条目与撤回后残留的空分片**不占地图、却占文件体积**。

做法只有一句话：**把"已经不是活记忆"的东西搬出分片**。

| 会被搬走 | 不会被搬走 |
|---|---|
| 被 `memory_correct` 取代 / 撤回、且**失效已满 `cleanupDays` 天**（默认 3；判据 `条目日期 ≤ 今天 − N`，**含边界**）的条目 | **活条目**（`- [日期] 事实`）—— 永不搬走，哪怕它很老、从没被检索过 |
| 因此变成 0 有效条目的**空分片**（连首行关键词头一起归档，文件删除） | 宽限期内刚取代完的历史（搬走它会让"取代可追溯"名存实亡） |
| —— | 宽限期内**被检索命中过**的失效条目（"刚被查过"通常意味着还在被追查，再等一轮） |

几个关键设计点：

- **活条目永不动**这一条是刻意的：**"很少有人问"不等于"没用了"**。自动按"很久没被检索"归档活分片，等于悄悄改变提示词内容 —— 本项目明确不做。
- **搬走的是原样的行**（连 `<!-- -->` 取代注释一起），所以归档是**可逆的纯文本操作**：需要复原就把行贴回原分片，行文本没有任何改写。
- **归档在每层自己的目录下**：`<层目录>/archive/<分片名>.md`，同一个分片的多次清理**追加到同一个文件**（否则归档目录会随清理次数线性膨胀）。
- **归档不进注入、也不被 `memory_search` 命中**；地图段尾只报一个数：`<!-- 记忆合计 N 片 / M 条 · 归档 K 件 · 全局层 … -->`。要清单就 `memory_cleanup`。
- **触发时机**（按要求实现）：**当天首次启动后延迟 `cleanupDelaySeconds`（默认 10）秒**跑一次，去重依据是每层状态文件里的 `lastCleanup` ⇒ **当天重启多少次都不会重复清理**，跨天自动恢复。延迟本身也有理由：启动瞬间宿主正在装配提示词，这时去读写记忆目录既慢又容易和在途写入抢文件。
- **后台清理拿不到 cwd**（那时可能还没有会话），所以它按 `storages/workspace.json` 里登记过的路径逐个清项目层。那是宿主的**内部格式**，因此读得很保守：解析失败就只清全局层、**不猜目录、不报错**。
- **没有任何分片的层什么都不写**（0.2.2，宿主内实测踩出来的修正）：层目录不存在、或里面一个 `*.md` 都没有时，清理**直接跳过** —— 不创建 `.agent-memory/`、也不写 `.state.json`。理由见下面那条实测记录：0.2.1 会给每个已知工作区都写一份状态文件，等于**在用户从没用过本插件的仓库里凭空建一个隐藏目录**。
- **`memory_cleanup` 是模型可见的入口**：`force` 默认 `true`（显式调用就是显式意图），传 `force: false` 才让"当天只跑一次"同样约束它。

> 🔎 **已在真实宿主里跑过**（第 10 轮）：一条 2026-09-30 失效的探针在 2026-10-03 重启后的自动清理里被整片搬走 —— `archive/archive-probe.md` 出现、原分片文件消失、同层活分片一动没动、地图脚注显示 `归档 1 件`。
>
> ⚠️ **状态文件**：每层多了一个 `.state.json`（检索命中记录 + 当天清理标记）。它**不是记忆正文** —— 不进注入、不参与检索，读坏了就退回空状态（对比：记忆正文坏掉必须可见）。命中记录按**日**粒度，所以同一天内重复检索**不产生写盘**。

> ⚠️ **0.2.1 的一个真实缺陷（0.2.2 修掉、0.2.4 一并重发，值得留档）**：后台清理会给**每个已知工作区**写状态文件，
> 包括那些从来没有记忆、因而没有 `.agent-memory/` 的仓库 —— 于是插件在用户没让它碰过的仓库里
> **凭空新建了一个隐藏目录**。这不是推测：宿主内实测在某个**只在这个工作区列表里出现过、
> 却从未写过任何记忆**的仓库的 `git status` 里，看到了一条与记忆无关的 `?? .agent-memory/`（里面只有一个 66 字节的 `.state.json`）。
> 这正是本项目最在意的形态 —— **工具在别人的仓库里留下了它不该留下的东西**，而且全程没有任何报错。
> 修法：**没有分片的层直接跳过，什么都不写**（代价只是每次启动多一次 `readdir`）。
> 教训：这次的信号**不在代码里、也不在单测里，而在文件系统上** —— 单测只断言"归档了什么"，
> 没断言"**没做什么**"。回归用例现在补上了这一条。

### 长内容：**文档 + 指针**（0.1.3 起写进注入纪律块）

一条记忆**只能是单行**（≤ `factBodyMax`，默认 2000 字符，见第 3 节的校验），所以**复盘 / 排查过程 / 长清单塞不进记忆**。
早期版本的处理方式只有一句"不该记：过程叙述"—— 结果是**过程永久丢失**：既没进记忆，也没别处可放。

现在纪律块明确给了正解，模型每轮都会读到：

```markdown
- **长内容**（复盘 / 排查过程 / 长清单）：记忆一条只能是单行，塞不下就别塞 —— 把原文写进仓库普通文档
  （如 `docs/postmortem-<主题>.md`，写它不受记忆守卫限制），记忆里只留**一行指针**：
  `根因/结论 + 症状关键词 + 文档路径`；复述时先 `memory_search` 命中该行、再 `read` 取全文 —— 关键词要写全，否则搜不到。
```

要点：

| 点 | 说明 |
|---|---|
| **文档放哪** | 仓库普通路径（`docs/…`、`NOTES.md`…）。写入守卫只拦**记忆目录**（`~/.dsh/memory-win/` 与 `<cwd>/.agent-memory/`），写别处不受影响 |
| **记忆里放什么** | **一行**：根因/结论 + 症状关键词 + 文档路径。关键词要写全（原始报错、文件名、命令），否则将来 `memory_search` 命中不到这行 |
| **⚠️ 内联上限（`inlineTextMax`，默认 160 字符）** | 小层内联档会把每条正文**截断到该上限**，超出的尾部在注入里消失。**0.1.4 起写入侧会给出 `⚠️` 提醒**（`memory_add` / `memory_correct` 的返回值里，见本小节末），但**截断本身仍在** —— 已存在的长条目照样会被切。所以长条目要写成「结论 + 指针」而不是把正文压进去。这是本项目自己踩过的坑：全局层 1 条 204 字符、项目层 3 条 243~365 字符的记忆，尾部长期没进过上下文，而且**没有任何报错** |
| **怎么复述** | `memory_search` 命中该行 → 拿 `path`/`line` → `read` 读文档全文。**记忆是索引，文档是正本** |
| **为什么不直接存进记忆** | 单行 + 写入上限（`factBodyMax`，默认 2000 字符）是条目格式的硬约束（多行会破坏 `- [日期] 事实` 结构、破坏去重与取代），不是为了省事 |
| **成本** | 纪律块固定开销 900 → 1,107（0.1.3 加「长内容」）→ **1,313 字符**（0.2.4 加「归档」，含失效天数与归档目录名）。它是**每轮都在的常量**且进前缀缓存 —— 换来的是"过程"这类需求第一次有了落点、以及"归档是什么"不再需要模型猜 |
| **地图段落整体** | 空态注入 **1,442 字符**（0.2.4 实测，cwd 缺失时更短）。归档**不进片列表**，只在段尾多几个字符 |

> 这条纪律同时补上了两个场景缺口：**长上下文里丢掉的细节**（细节写进文档、记忆留指针）与
> **严重 BUG 的过程复述**（复盘进 `docs/`，记忆只存一行因果）。判定与依据见实施进度文档 §5.5。

#### 写入侧提醒：160 截断不再无声（0.1.4）

`memory_add` 与 `memory_correct` 在正文超过 **160 字符**时，返回值里会带一个**不阻断**的 `warning`，
工具输出渲染成 `⚠️`：

```text
已写入 project/glossary
  path=.agent-memory/glossary.md line=3
  entry=- [2026-10-02] …（很长的一条）
  该分片现有 1 条。
  ⚠️ 这条正文 243 字符，超过内联档的显示上限 160：在条目数 ≤ 8 的层里，注入只会显示前 160 字符，
     **尾部会静默消失**（正文已完整落盘，可用 memory_search 取回）。建议改成「结论 + 指针」：
     长正文写进仓库文档，这条只留结论与文档路径。
```

为什么要加它：上面那条坑是靠 `parseEntries` 把所有记忆文件**量了一遍**才发现的 ——
4 条超长记忆全都**合法写入成功**、注入里静默丢尾，之前没有任何信号。现在改成**写入时就可见**。

两个数字别混：

| | 配置键 | 默认 | 行为 |
|---|---|---|---|
| **写入上限** | `factBodyMax` | 2000 字符 | 超了**拒绝**，错误信息可执行（`validateFactBody`） |
| **显示上限** | `inlineTextMax` | 160 字符 | 超了**截断 + 提醒**，正文照常完整落盘 |

**阈值只有一个定义处**：两者的来源是 `lib/config.js` 的 `CONFIG_DEFAULTS`（0.2.4 起可配置），
渲染（`lib/map.js`）与提醒（`lib/format.js` 的 `inlineTruncationWarning`）都**从配置取同一个数**，
且两边都用同一个 `oneLine()` **压平空白后**再计长 —— 否则会在边界上互相矛盾（本项目吃过一次
"同一套规则被复制成两份"的亏，见第 3 节限制 2）。回归用例里专门有"正好等于上限不提醒"、
"压平后才计长"、以及"**改了配置之后两边同时跟着变**"三类的边界断言。
另外有一条**交叉约束**在启动时校验：`inlineTextMax` 不得大于 `factBodyMax`，
否则提醒永远不可能触发（超限正文会先在写入校验里被拒）。

#### 同一套分工的另一个用例：grilling 产出的术语表 / ADR

`grill-with-docs` 会把术语**逐条**写进仓库根的 `GLOSSARY.md`（多 context 时是各 context 的
`GLOSSARY.md` + 根 `GLOSSARY-MAP.md`），决策写进 ADR；`grill-me` 则**不落盘**（stateless），
所以后者默认跨会话零复用，要复用必须显式写文件。**术语表本身不要进记忆条目** —— 它每条术语
3 行（`**术语**:` + 定义 + `_Avoid_:` 别名），还有 `Relationships` / `Flagged ambiguities` 两节，
塞不进单行。正解同样是**文件做正本、记忆做路由**：

```js
// 每个 context 一条指针；keywords 带上 _Avoid_ 里的废弃词
memory_add { target: "project", shard: "glossary",
  keywords: "术语表 glossary domain 词汇 废弃词 backlog manager backlog backend issue host",
  fact: "项目术语表：GLOSSARY.md（含 …；多 context 见 GLOSSARY-MAP.md）" }
```

为什么要带**废弃词**：检索时片名与关键词也参与匹配，所以将来谁用了 `_Avoid_:` 里那个旧词提问，
也能命中这行指针，再由 `read` 进 `GLOSSARY.md` 看解析结果。

> ⚠️ **一处实测出来的取舍**：别名只写进**片级 keywords** 会让**整片条目**都命中；
> 写进**条目正文**才精确命中该条。所以术语表**只留一条指针**时用 keywords 最合适；
> 若你按术语拆成 N 条，别名要放各自的条目正文，别堆到 keywords 里。
>
> 另外：`GLOSSARY.md` 提交进 git ⇒ 跨机器也在；而 `.agent-memory/` 默认被 gitignore ⇒
> **记忆指针带不走**。重要项目的指针要么把 `.agent-memory/` 也提交，要么把指针写进仓库文档。

## 3. 安全与稳健性（明确边界）

| 机制 | 说明 |
|---|---|
| **凭据扫描** | 默认 8 类模式（`sk-` / `sk-ant-` / `AKIA` / `gh[pousr]_` / `xox[bpars]-` / 私钥块 / `Bearer` / 凭据赋值；可用 `credentialPatterns` **整段替换**）。命中即 **deny**，且**只报模式名与行号，绝不回显匹配值** —— 否则拒绝原因会把凭据复制进模型上下文与日志。`memory_correct` 的 `replacement` 同样过这道闸 |
| **写入守卫** | 拦住用原生 `write`/`edit` 直改记忆文件，引导改用 `memory_add` / `memory_correct` |
| **路径逃逸** | `shard` 名称拒绝 `..`、分隔符与 Windows 保留字符，并做解析后的包含性复核（`globalSubpath` / `projectDir` / `archiveDir` 这些**配置项**走同样的校验，配置不该是漏的那个） |
| **正文保留语法** | 条目正文不得含 `-->`（会提前闭合取代标记的注释），也不得自带行尾 `[fix:… of #…]`（取代机制的保留语法） |
| **取代不得回填** | `memory_correct` 拒绝「替换日期早于被取代者」的条目，避免时间线倒挂；**同日取代是允许的** —— 刚记下就发现错了是最常见的情形，而旧条目此时已被注释、不再是活条目，不产生环 |
| **归档只搬失效条目** | 容量策略只移动**已失效**（被取代 / 撤回）且已过宽限期的条目与空分片；活条目永不搬走，且搬走的行**原样保留**、可手工复原（见第 2 节） |
| **原子写** | 同目录临时文件（带 pid + 随机数）→ `rename` 覆盖 |
| **并发** | 每文件一条 promise 串行链 + **写前重读**（分片与 `.state.json` 共用 `lib/fs-utils.js` 这一套；**绝不允许对同一文件嵌套两层链**，那会自死锁）。20 个并发追加的回归测试断言一条不丢 |
| **fail-visible** | 注入渲染失败、项目层不可用、配置非法等情形都**留下可见痕迹**（配置非法直接**拒绝启动**），不静默返回空或带着半截配置跑 |

### 声明清楚的限制

1. **守卫只覆盖原生 `write`/`edit`。** `pwsh`、MCP 工具、其它插件都能绕过。**它是防手滑，不是防对抗。**
2. **两条守卫路径同时挂载，取并集。** `tools.guard()`（单调，不可被后续监听者放行）与 `tools/pre-execute` waterfall **都注册**，二者共用同一判定 `directWriteDenial()`，因此覆盖面一致（全局层 + 项目层）。
   > 此处曾是一个**真实缺陷**：早期实现写成二选一（`if (tools.guard) {...} else {...}`），由于 DSH 有 `tools.guard`，项目层那条分支**从不执行**，`<repo>/.agent-memory/*.md` 的直写**完全不被拦** —— 已在真实宿主里实测到（写入竟然成功落盘）并修复。教训：**单调性更强 ≠ 覆盖面更广**。
   >
   > 另一处曾判断错误：我以为同步 guard "拿不到 cwd"，实际宿主在 `exec` 上就带着 `agent`（`guardReason(exec)` 里显式读它），所以同步 guard 同样能解析项目层。
3. **项目层守卫只保护「会话 cwd 下」的 `.agent-memory`。** 项目层 = 一个会话一个项目根。若某个**子目录**里也有 `.agent-memory`（它自己可能是另一个会话的工作目录），在父目录会话里写它**不会被拦**。这是设计后果而非 bug；若将来要支持多项目根，需改成"保护工作区树下所有 `.agent-memory`"。
4. **跨进程并发写不做锁。** 串行化是**进程内**的（DSH 插件跑在宿主进程内，这在桌面版是成立的）。锁文件方案被刻意放弃 —— `dsh-memory-evolve` 的 pid 存活探测锁在 Windows 上语义不可靠。
5. **不做 shell 解析。** 不解析 `pwsh` 的重定向目标去判断"是否在改记忆"。这类启发式在 Windows 上收益低且正是误报来源。
6. **无自有设置面板。** 启停用 DSH 原生的插件开关（见第 5 节，**实测热生效、不需重启**）；行为阈值 0.2.4 起**可配置**，但入口只有 profile patch 的 `config:` 段 —— **没有自己的设置页**（DSH 不会为任意插件自动渲染配置表单，见第 5 节与限制 13）。
7. **不做向量检索、不做后台巩固、不调用模型。** 这是刻意的取舍，不是未完成。
8. **长内容不是记忆的形态。** 一条记忆是**单行且 ≤ `factBodyMax`**（默认 2000 字符），因此复盘、排查时间线、长清单**写不进记忆** —— 正解是「文档 + 指针」（见第 2 节）。注意：把这份文档**手工写进记忆目录**同样会被守卫拦（守卫拦的是原生 `write`/`edit` 落到记忆目录，**包括新建文件**），所以文档要放在仓库普通路径。另外，**内联档每条正文只显示前 `inlineTextMax` 字符**（默认 160，超过部分被截断，正文仍完整落盘）；0.1.4 起写入侧会给 `⚠️` 提醒，但**已有的长条目照样会被切** —— 所以长度要靠「结论 + 指针」控制，而不是靠提醒。
9. **归档只针对失效条目。** 已被取代 / 撤回的条目与空分片会在失效满 `cleanupDays`（默认 3）天后被搬进 `<层目录>/archive/`（换回"文件不再单调增长"，代价是归档件不再参与检索）。**活条目永不被归档** —— 包括"很老且从没被检索过"的那些，因为"很少有人问"不等于"没用了"。归档件原样保留失效行，需要时可手工贴回分片复原。
10. **已装入真实宿主并逐项验证通过**（见第 4 节）：两层的写入守卫、四类 `reason`、同日取代、以及设置里那个开关的**开/关往返**都实测过，均为热生效。0.2.x 的配置层与容量策略也已**重启实测**（第 9 轮）：自动清理按时跑、当天不重复、命中真的落盘、纪律块更新到位；复验还抓到并修掉了缺陷 D6。**真实的归档动作**已在第 10 轮（0.2.4）实测通过（含整片归档、删原文件、活条目不动、地图脚注报数）。
11. **后台清理的项目层依赖宿主的 `storages/workspace.json`。** 那是宿主的**内部格式**（本项目唯一读它的地方），格式若变则后台清理只覆盖全局层 —— 读不懂就**少扫一层**，不猜目录、不报错（全局层清理不受影响）。当次会话所在工作区不受此限：它走 cwd。
12. **归档件不会被自动读回。** 归档不进注入、也不被 `memory_search` 命中（这正是"搬走"的意义）。要读旧结论得用 `memory_cleanup` 拿路径后 `read`，或把行贴回分片。**没有**"归档检索"这种半自动通道。
13. **配置只能改 profile 的 `cordis.patch.yml`，且改完要重启。** DSH 不会为任意插件渲染设置表单；而配置是在**插件模块**里读的，profile 的 HMR 只监听 patch 文件（环境事实 5）⇒ 改 `config:` 段必须重启桌面版才生效。

### 环境事实（踩到的坑，值得记录）

1. **`node --test test/` 在受限沙箱下会 `spawn EPERM`。** 它把每个文件 fork 成子进程并用管道收 stdio，而沙箱禁止子进程管道通信 —— 表现是**测试文件全报 `spawn EPERM`、一条断言都跑不到**，看起来像测试失败，实际是运行器跑不起来。因此改用 `test/run.mjs` 在**同进程内**依次 import，断言与结果完全一致。
2. **沙箱临时目录会被重映射**（`$env:TEMP` 实际解析到 `...\Temp\dsh-<random>\...`）。测试因此全部使用 `mkdtempSync`，不依赖固定路径。
3. **沙箱禁止写 `~/.dsh`**（工作区之外）。因此 `dsh plugin add` 与 `plugin_manager install_bundle` 都必须在放宽权限后才能执行；普通桌面版用户没有这个限制。
4. **本机系统日期早于某些文档落款** —— 首次演示写入"明天"的条目被**正确拒绝**，反向验证了未来日期守卫生效。
5. **profile 的 HMR 只监听 patch 文件，不监听插件模块文件。** 改 `lib/*.js` **不会**热重载，需要重启桌面版；而「设置 → 插件」的开关是另一条路径，它走 HMR ⇒ **热生效**（见第 5 节）。
6. **`dsh plugin add` 的进程有时会挂住不退出**（依赖与 lockfile 均已写好、无子进程残留）。不要一直等它；确认输出后结束该进程即可。另有一次在最后写 `package.json` 时报 `EPERM rename`（文件被占用），**重跑一次 add 即成功**。
7. **同一文件绝不能嵌套两层写入串行链（会自死锁）。** 0.2 初版把写入写成
   `serializeWrite(file, async () => { …; await writeTextSerialized(file, next) })` ——
   外层 op 要等内层写完，而内层排在**外层自己**后面，于是这条 promise 永不 settle：
   表现是 `memory_add` 整个挂住、Node 报 `Promise resolution is still pending but the event loop has already resolved`。
   修法是**取消嵌套**：读-改-写整个包进同一个 op，由 `lib/fs-utils.js` 的 `writeAtomically` 负责唯一落盘。
   > 排查过程本身也值得记一笔：这个现象看起来像"fs 调用被沙箱挡住了"，实际是纯逻辑死锁 ——
   > 定性靠的是**给 op 打点**（`op1 ran` 出现、`op2` 不出现），而不是继续猜沙箱。

## 5. 怎么用

```powershell
# 1) 跑测试
cd dsh-memory-win
node test/run.mjs

# 2) 打包成 tarball，并自动复制到 ~/.dsh/plugin-tarballs/
node scripts/pack.mjs

# 3) 装进桌面版 profile（会改动 ~/.dsh/profiles/desktop，建议先备份）
dsh plugin --profile desktop add "file:C:/Users/<你>/.dsh/plugin-tarballs/dsh-memory-win-0.2.4.tgz"
```

### ⚠️ 为什么必须用 tarball，而不是 `file:` 目录

**这是本项目踩过的最贵的一个坑，务必先读。**

profile 配置为 `nodeLinker: hoisted`，`file:` **目录**依赖会被 pnpm 解析成
`{directory, type: directory}` 并做**拷贝快照**（**不是**符号链接）。实测：

| 事实 | 证据 |
|---|---|
| profile 里的 `node_modules/dsh-memory-win` 是**真实目录拷贝** | `LinkType`/`Target` 皆空，非 symlink/junction |
| **改了仓库源码，宿主不会看到** | 逐文件哈希比对：副本停在安装时刻，七个源文件全部与源码不同 |
| `install_bundle` **不会**刷新它 | 目录 spec 未变 ⇒ pnpm 判定"已满足" ⇒ `changed:false`，不重拷文件 |

**后果**：它让"改了却看不到效果"**伪装成代码缺陷**。本项目连续两轮把"部署未同步"
误判为插件 bug（先是守卫不生效、后是工具丢失），直到对 profile 里那份文件取哈希才定性。

**tarball 解决它 —— 但前提是 _文件名必须变_。** tarball 依赖带 integrity 哈希，然而实测发现：

| 操作 | 结果 |
|---|---|
| 替换**同文件名**的 tarball（内容变了）后重新 `add` | pnpm 报 `downloaded 1`，但 **`node_modules` 里的文件没被改写** —— 因为 spec（路径）未变，照旧跳过 |
| **升版本号** → 新文件名 → 重新 `add` | `added 1`，全部文件**逐字节一致** ✅ |

⇒ **每次改动源码后必须升 `package.json` 的 `version`**，再走下面的流程。否则坑只是从
"目录依赖"换到了"tarball 依赖"，一样会跑到旧代码。`scripts/pack.mjs` 在"目标已存在同名但内容不同的 tarball"时会直接警告。

```powershell
# 每次改动源码后的固定流程
# 1) 升版本号（必须！否则下面的 add 会静默跳过）
#    编辑 package.json 的 "version": "0.2.4" -> "0.2.5"
# 2) 打包并复制到 ~/.dsh/plugin-tarballs/
node scripts/pack.mjs
# 3) 装新版本（路径变了，pnpm 才会真正重装）
dsh plugin --profile desktop add "file:C:/Users/<你>/.dsh/plugin-tarballs/dsh-memory-win-0.2.5.tgz"
# 4) 重启桌面版
```

> **排查同类问题的手段**：怀疑"改了没生效"时，**直接对 profile 里那份文件取哈希**
> 与源码比对，而不是反复重装或重启。这一步能立刻区分"代码不对"与"没跑到新代码"。
> 本项目为此付出了连续两轮误判的代价，才有这一条。
>
> 比对范围是 `index.js` / `package.json` / `cordis.patch.yml` / `lib/*.js` —— **`README.md`
> 不参与运行**，所以你自己改过 README 之后，只有它会与 profile 里的那份不同，属正常。

### ⚠️ `plugin add` 只装依赖，**不会挂载**（首次装入必须再 enable 一次）

这一步做了两件事：把 `dsh-memory-win` 写进 profile 的 `dependencies`、并把 tarball 解压进
`node_modules`。它**不会**把包加进 `dsh.profile.bundles` —— 而 bundle 列表才是真正决定
"哪个 patch 层被应用"的东西（本插件的 patch 由 `dsh.bundle.patch` 声明，靠被列进 bundles 生效）。

所以**首次装入**还必须再启用一次 bundle：

```
plugin_manager { action: "install_bundle", target: "dsh-memory-win" }
```

返回 `{"stage":"enable","changed":true,"application":"restart-required"}` 即成功。
成功后可核对 `list_bundles`：本插件应显示 `installed: true, removable: true` 并带 `rows`
（与 `dsh-our-free-model` 同构）—— 这正是「设置 → 插件」里那个开关可用的条件。

> **升级时不必重复这一步**：`dsh.profile.bundles` 是持久状态，升版本后它仍在列表里，
> 照上面四步走（升版本 → 打包 → add → 重启）即可。拿不准就先 `list_bundles` 核对一下。

### 关于那个开关（实测：**热生效，不需要重启**）

启用后，「设置 → 插件」里会出现 **dsh-memory-win** 一行，带一个与 `Our Free Model` 完全同构的开关。
这是 **DSH 原生的插件启停**，不是插件自己做的：它绑定 loader 条目的 `disabled` 选项
（`pluginManager.setBundleEnabled` / `setPluginEnabled`）。**插件侧无需任何代码。**

实测确认（在 GUI 里真的点过开与关）：

| 检查 | 关闭时 | 重新打开后 |
|---|---|---|
| 系统提示词地图段 | **消失** | **回来** |
| `list_plugins` 条目总数 | 189 → **188** | 回到 **189** |
| loader 条目 | 不在列表中 | `include:dsh-memory-win`，`fiberPhase: active` |
| `memory_*` 工具 | 卸载（`unknown tool`） | 四个全部可用 |

⇒ **点完立即生效**（下一轮就能看出效果）、**干净卸载**（条目数正好 −1，无残留注入）、
**重启后关闭状态保持**、**往返不留残留**。

**重要：不要用 `install_bundle` 去重新打开插件。** 那走的是 `installBundle` 路径，里面有
`if (Object.hasOwn(before, name)) return 'restart-required'` —— bundle 已在 `dependencies` 里，
于是**白白要求一次重启**。直接用设置里那个开关即可，它没有这个覆盖，是热生效的：

```js
// setBundleEnabled 的实际判定（宿主实现）
application: ownerContext.get('hmr') !== undefined ? 'applied' : 'restart-required'
// 本 profile 的 HMR 已加载并活跃 ⇒ applied
```

**关闭 ≠ 卸载 ≠ 删数据**：`dependencies` 里的 tarball 依赖保留、`node_modules` 里的文件保留、
记忆数据完好。关闭只是"停止启动"。

注意「设置 → 插件」里带 `readOnlyReason` 的内置 bundle 是**锁定的**（开关灰掉）；
只有 `removable: true` 且有 `rows` 的条目可切换 —— 这也是必须先 `install_bundle`
（而不是手工往 `cordis.patch.yml` 插一条）的原因：手工插的行不在 bundle 注册表里，可能拿不到可用开关。

### 数据位置

| 层 | 路径 |
|---|---|
| 全局 | `%DSH_HOME%`（默认 `C:\Users\<你>\.dsh`）`\memory-win\global\*.md` |
| 项目 | `<会话工作目录>\.agent-memory\*.md` |
| 归档（每层各一个） | `<层目录>\archive\<分片名>.md` —— 不在注入里，用 `memory_cleanup` 查看 |
| 状态（每层各一个） | `<层目录>\.state.json` —— 检索命中记录 + 当天清理标记，不是记忆 |

项目层放在仓库内、且默认被 `.gitignore` 忽略（`dsh-memory-win/.gitignore` 只覆盖自身仓库；**使用者的仓库需自行忽略 `.agent-memory/`**）。

### 配置（0.2.4 起）

0.1.x 的所有行为阈值都是硬编码常量，改任何一个都要改源码、重打包、重启。现在它们收敛到
`lib/config.js` 一个模块，外部入口是 **profile 的 `cordis.patch.yml`**：

```yaml
# ~/.dsh/profiles/desktop/cordis.patch.yml
- id: dsh-memory-win
  name: 'dsh-memory-win'
  config:
    inlineTextMax: 200        # 只写你要改的键，其余自动取默认
    cleanupDays: 7
```

> ⚠️ 宿主对这条 patch 做的是**整段替换** bundle insert 的 `config: {}`，**不是深合并** ——
> 所以"只写你要改的键"是靠**插件自己补默认值**做到的（`normalizeConfig`），不是靠宿主。
> 这一点是实读 `cordis-plugin-include` 的 `applyEntryPatches` 得到的，不是推测（见第 4 节）。

全部键（默认值 / 合法范围）：

| 键 | 默认 | 范围 | 说明 |
|---|---|---|---|
| `inlineTextMax` | 160 | 1–100000 | 内联档每条正文的**显示**上限；超了截断 + `⚠️` 提醒（正文仍完整落盘） |
| `factBodyMax` | 2000 | 1–1000000 | 单条正文的**写入**上限；超了直接拒绝。**必须 ≥ `inlineTextMax`** |
| `inlineThreshold` | 8 | 1–10000 | 某层条目数不超过它时逐条内联，超过则切"每片一行"的地图档 |
| `keywordsMaxChars` | 120 | 1–10000 | 片级关键词上限（地图档每条片行只有 ~68 字符，关键词不该喧宾夺主） |
| `globalSubpath` | `["memory-win","global"]` | 非空字符串数组 | 全局层在 `DSH_HOME` 下的子路径 |
| `projectDir` | `.agent-memory` | 非空单行串 | 项目层目录名（相对会话 cwd） |
| `archiveDir` | `archive` | 非空单行串 | 归档目录名（相对各层目录） |
| `stateFile` | `.state.json` | 非空单行串 | 每层状态文件名；不能与 `archiveDir` 同名 |
| `cleanupDays` | 3 | **1**–10000 | 失效条目**满几天后**可归档。判据：`失效日期 ≤ 今天 − cleanupDays`（**含边界**，即"满 N 天"就该搬；默认 3 ⇒ 3 天前失效的今天就归档）|
| `cleanupDelaySeconds` | 10 | 0–86400 | 当天首次启动后延迟多少秒触发清理（0 = 立即，测试用） |
| `cleanupEnabled` | `true` | 布尔 | 是否启用容量策略（后台清理 + `memory_cleanup`） |
| `maxProjectLayers` | 20 | 0–10000 | 一次后台清理最多处理多少个已知工作区的项目层 |
| `credentialPatterns` | `null` | 对象或 `null` | `{ 模式名: 正则字符串 }`，**整段替换**内置 8 类；`null` = 用内置表 |
| `archivePointer` | （见源码） | 非空串 | 纪律块里那句"归档是什么、去哪找"的文本 |

**启动时校验，配错了拒绝启动**（不会带着半截配置跑）：类型、范围、路径逃逸，以及两条**交叉约束**：

1. `inlineTextMax > factBodyMax` ⇒ 抛错。否则"写入侧截断提醒"永远不可能触发 —— 超过显示上限的正文会先在写入校验里被拒；
2. `stateFile === archiveDir` ⇒ 抛错（状态文件会被当成归档目录）。

**改完必须重启桌面版**（配置在插件模块里读，而 profile 的 HMR 不监听插件模块文件 —— 环境事实 5）。
没有自己的设置页：DSH 不会为任意插件自动渲染配置表单（见第 7 节的问题 3，客户端半身仍未做）。

### ⚠️ 从 `.dsh-memory` 升级（破坏性改名）

项目层目录已从 `.dsh-memory/` 改名为 **`.agent-memory/`**（去掉产品前缀，便于其它 agent 读取；保留前导点作为隐藏目录）。
**旧目录不会被自动迁移** —— 插件只读新目录，所以不迁移就等于项目层记忆"消失"了。

文件格式完全一致，手工搬一次即可：

```powershell
# 在目标仓库根目录执行；合并同名分片请自行确认无冲突
Rename-Item .dsh-memory .agent-memory
# 若新旧目录都已有内容，改为逐个搬文件：
# Get-ChildItem .dsh-memory\*.md | Move-Item -Destination .agent-memory\
```

搬完后建议跑一次 `memory_list` 确认条数符合预期。

> 不自动迁移是刻意的：往用户仓库里悄悄改名/移动文件属于不可逆操作，
> 而"旧目录还在、新目录为空"这种状态是**可见的**（`memory_list` 报 0 条），不是静默失效。

## 6. 代码结构

```
index.js             插件挂载：initConfig(config) + section + 五工具 + 双路守卫 + 当天首次清理定时器
                     （inject: ["systemPrompt", "tools"]）
lib/config.js        配置层：默认值 / 解析顺序 / 启动校验 / 凭据模式表（0.2.4）
lib/paths.js         路径与 slug —— Windows 适配核心，全部调用时求值；含日期窗口工具
lib/format.js        纯函数：条目格式/日期/凭据/去重、条目 id、取代元数据、{{ 中和、截断提醒
lib/fs-utils.js      文件读写唯一实现处：安全读、原子写、按文件串行链（分片与状态共用，0.2.4）
lib/state.js         每层 .state.json：检索命中记录、当天清理标记、归档判定纯函数（0.2.4）
lib/engine.js        存储：分层、扫描、检索、原子追加/取代、容量策略（cleanupLayer/runCleanup，0.2.4）
lib/map.js           地图档注入渲染 + 注入纪律块（取回/写入/长内容指针/修正/归档）
lib/tools.js         五个 ToolDefinition
lib/guard.js         write/edit 直写守卫（两条路径共用判定）
lib/context.js       cwd 提取（守卫与工具共用一份，避免两处漂移）
scripts/pack.mjs     打包 tarball 并复制到 ~/.dsh/plugin-tarballs/（覆盖同名不同内容的包时警告）
test/                146 个用例 + 同进程运行器（test/run.mjs）
```

分层原则：**纯判定与 I/O 分离**。`lib/format.js` 完全不碰文件系统，`lib/config.js` 的 `normalizeConfig`
也是纯函数，因此判定内核可以被穷举测试 —— 参考插件把这类判定与文件读写混在同一个巨型文件里
（`dsh-auto-memory` 的 `index.js` 1.08 MB），导致"想测判定"必须先把整个宿主上下文搭起来。

另一条 0.2.4 才写下来的纪律：**`config.js` 不 import `format.js`**（否则循环依赖）。
内置凭据模式表由 `format.js` 在模块求值时**反向登记**进配置层（`setDefaultCredentialPatterns`），
扫描侧统一走 `credentialPatternList()` —— 于是"默认 8 类"与"配置替换表"只有一个出口。

## 7. 已知限制与后续

**本 demo 有意没做的**：自有设置面板、`memory_delete`（删除条目）、片级关键词的自动生成、
子代理检索路由的程序化强制、跨进程锁、多语言、归档内容的**自动**读回、以及本 README 之外的详细设计文档。

**已定的用法边界（不是缺口，是分工）**：**长内容不进记忆** —— 复盘、排查时间线、长清单写进仓库文档，
记忆里只留一行指针（见第 2 节「长内容：文档 + 指针」）。这条已写进注入纪律块，模型每轮都会读到。
它补上了原先"过程叙述被禁止、于是过程永久丢失"的空档。

**已定第二条用法边界**：**归档不是删除，但也不是第二层记忆** —— 归档件不进注入、也不被
`memory_search` 命中（见第 2 节「容量策略」）。需要旧结论时用 `memory_cleanup` 拿路径再 `read`。

**后续补充设计时需要回答的问题**：

1. ~~**容量策略**（最优先）：是否归档、何时触发、归档后地图如何呈现？~~ → **0.2.4 已落地**（见第 2 节）：
   只归档**已失效条目**（失效满 `cleanupDays` 天）与空分片；触发时机是当天首次启动 + 延迟 10 秒，
   按每层状态文件里的 `lastCleanup` 去重；地图与 `memory_list` 只报一个**归档件数**，清单走 `memory_cleanup`。
   **活条目仍不进归档**（"很少有人问" ≠ "没用了"）—— 所以"文件体积"这条压力的解是**部分**的：
   它随"取代/撤回的次数"增长，不再随"这些历史的存活时间"增长。
2. ~~**注入档位 / 内联阈值可配置**~~ → **0.2.4 已落地**（`lib/config.js`，见第 5 节「配置」）。
   仍未做的是**客户端表单**：DSH 不会为任意插件自动渲染配置表单，所以现在只有"改 patch 的 `config:` 段"这一条路。
3. **是否需要客户端半身**（设置面板 / 记忆浏览页 / 关键词编辑 UI）—— 也是上一条的前置。
4. **一条条目被多次取代后的版本链检索**：`fix` 只记直接前驱（`of #id`），要回答"这条结论被改过几次、为什么"需顺着链回溯；目前靠 `read` 全文人工追溯。注意归档后这条链会**跨文件**（活条目在分片、被取代的祖先在归档件里），追溯成本上升。
5. **条目修订是否要行级编辑**：当前取"取代"语义已避开整条替换的数据丢失风险
   （`dsh-memory-evolve` 的 `memory-consolidate` 自述"更正一条多段记忆时只写了新句子，其余段落整条丢失"）。
6. **是否需要外部判定钩子**：参考 `dsh-memory` 的 `writeGuard:"full"`，可接任意 LLM 脚本判断"这条值不值得记"。注意它在 Windows 上因硬编码 `/bin/zsh` 而抛穿 —— 若要实现，必须用纯 Node 方式调用而非 shell。
7. **召回增强**（同义词 / 前缀 / OR 兜底，或"命中 0 条"时自动放宽重试一次）：纯 JS 可实现、不需要向量库。
   这是场景自评里"长上下文遗漏细节"那条剩下的真短板（另一半是写入侧靠模型自觉）。
8. **归档的检索通道**：目前归档**只能手工读**。如果要"需要时也能搜到旧结论"，得先回答
   "何时该把归档重新纳入召回"—— 那已经不是存储问题，而是**证据强度**问题（旧结论只该作为历史参考）。
